1. System Overview & Architecture

DNS Attack Defender (DAD) is a local DNS proxy that intercepts all DNS traffic on a macOS machine via the built-in PF (Packet Filter) firewall. Every DNS query passes through a 12-stage detection pipeline before being forwarded to an upstream resolver. Malicious queries are blocked inline; suspicious activity triggers real-time alerts via macOS Notification Center, JSONL logs, and optional webhooks.

2. PF Firewall Redirect — Traffic Interception

macOS includes the OpenBSD PF (Packet Filter) firewall. DAD uses a PF anchor to transparently redirect all DNS traffic (UDP/TCP port 53) to the local proxy on port 5353. This means no application configuration is needed — every DNS query from every app is intercepted.

2.1 How PF Anchors Work on macOS

┌─────────────────────────────────────────────────────────┐
│  Application (Safari, curl, etc.)                        │
│  Issues DNS query to 1.1.1.1:53                          │
└──────────────────┬──────────────────────────────────────┘
                   │ UDP packet: src=:12345 dst=1.1.1.1:53
                   ▼
┌─────────────────────────────────────────────────────────┐
│  macOS Kernel — Network Stack                            │
│                                                          │
│  1. Packet enters on lo0 (loopback)                      │
│  2. PF anchor "dnsattackdefender" evaluates RDR rules    │
│  3. Rule: rdr pass on lo0 inet proto udp                 │
│          from any to any port 53 → 127.0.0.1 port 5353  │
│  4. Destination rewritten: 1.1.1.1:53 → 127.0.0.1:5353  │
│                                                          │
│  Original dst preserved in pf "divert" metadata          │
└──────────────────┬──────────────────────────────────────┘
                   │ Redirected packet: dst=127.0.0.1:5353
                   ▼
┌─────────────────────────────────────────────────────────┐
│  DAD Proxy (Go, listening on 127.0.0.1:5353)             │
│  Receives query, processes through pipeline              │
│  Forwards to upstream via DoH (encrypted)                │
└─────────────────────────────────────────────────────────┘

2.2 PF Rules Generated by DAD

# Generated by DAD — PF anchor "dnsattackdefender"

# IPv4 UDP redirect
rdr pass on lo0 inet proto udp from any to any port 53 → 127.0.0.1 port 5353

# IPv4 TCP redirect (for large responses / zone transfers)
rdr pass on lo0 inet proto tcp from any to any port 53 → 127.0.0.1 port 5353

# IPv6 UDP redirect
rdr pass on lo0 inet6 proto udp from any to any port 53 → ::1 port 5353

# IPv6 TCP redirect
rdr pass on lo0 inet6 proto tcp from any to any port 53 → ::1 port 5353

3. Full Detection Pipeline (12-Stage)

Every DNS query enters the pipeline at the top and flows through each stage sequentially. If any stage blocks the query, processing stops immediately and a response (NXDOMAIN, REFUSED, or dropped) is sent to the client. Only queries that pass all blocking stages reach the upstream resolver.

Forward (to upstream)

Design principle: Blocking stages run in order of cost (cheapest first). Rate limiting is O(1) hash lookup. Blocklist is O(1) hash + O(k) suffix check. Entropy/DGA are O(n) per label. DNSSEC validation happens only after upstream response. This minimizes CPU for legitimate traffic.

4. Stage 1: Rate Limiting (DDoS / Amplification)

Rate limiting is the first defense against volumetric DNS attacks. DAD uses a token bucket algorithm per client IP address, with separate buckets for general queries and NXDOMAIN responses (water torture detection).

4.1 Token Bucket Algorithm

                    ┌──────────────────────────────────┐
                    │     TOKEN BUCKET (per client IP)   │
                    │                                    │
                    │  Capacity: per_ip_qps (e.g., 50)  │
                    │  Refill rate: per_ip_qps / sec    │
                    │  Window: 15 seconds rolling        │
                    │                                    │
                    │  tokens: 47.3                      │
                    │  nxdomain_tokens: 8.1              │
                    │  last_refill: 2026-08-01T22:33:15  │
                    └──────────────┬─────────────────────┘
                                   │
           Query arrives ──────────┤
                                   │
                    ┌──────────────▼─────────────────────┐
                    │  1. Calculate elapsed since refill │
                    │  2. tokens += elapsed * refill_rate│
                    │  3. Cap at per_ip_qps              │
                    │  4. If tokens < 1.0 → BLOCK        │
                    │  5. tokens -= 1.0                  │
                    │  6. Return ALLOW                   │
                    └──────────────┬─────────────────────┘
                                   │
                    ┌──────────────▼─────────────────────┐
                    │         ACTION SELECTION           │
                    │                                    │
                    │  cfg.action = "drop"     → drop    │
                    │  cfg.action = "truncate" → TC=1    │
                    │  cfg.action = "delay"    → 100ms   │
                    └────────────────────────────────────┘

4.2 Data Flow Detail

4.3 NXDOMAIN Rate Limiting (Water Torture Defense)

A separate token bucket tracks NXDOMAIN responses per IP. When an attacker floods the resolver with queries for non-existent subdomains, each NXDOMAIN response debits the NXDOMAIN bucket. When exhausted, further NXDOMAIN-generating queries are dropped.

Client sends: a8k3m2.example.com  → NXDOMAIN  (nxdomain_tokens: 9→8)
Client sends: b9x4n3.example.com  → NXDOMAIN  (nxdomain_tokens: 8→7)
Client sends: c7y5o1.example.com  → NXDOMAIN  (nxdomain_tokens: 7→6)
...
Client sends: k2p9q8.example.com  → NXDOMAIN  (nxdomain_tokens: 0→BLOCKED)
Client sends: l3q0r9.example.com  → DROPPED   (bucket empty, rate limited)

5. Stage 2: Zone Transfer Blocking (AXFR/IXFR)

Zone transfers (AXFR/IXFR) are DNS operations that replicate entire zone files between nameservers. If exposed to untrusted clients, attackers can enumerate all DNS records in a zone — a critical reconnaissance vector.

5.1 Data Flow

┌──────────────────────────────────────────────────┐
│  DNS query arrives with Question section          │
│  qtype = 252 (AXFR) or qtype = 251 (IXFR)        │
└────────────────────┬─────────────────────────────┘
                     │
                     ▼
┌──────────────────────────────────────────────────┐
│  Check: cfg.ZoneTransfer.BlockAXFR == true       │
│  AND   q.Qtype == dns.TypeAXFR (252)             │
│                                                    │
│  Check: cfg.ZoneTransfer.BlockIXFR == true       │
│  AND   q.Qtype == dns.TypeIXFR (251)             │
└────────────────────┬─────────────────────────────┘
                     │
          ┌──────────┴──────────┐
          │                     │
     Match found           No match
          │                     │
          ▼                     ▼
┌─────────────────┐   ┌─────────────────────┐
│  AlertOnly?     │   │  Continue to        │
│                 │   │  Stage 3: Blocklist │
│  YES → log only │   └─────────────────────┘
│  NO  → REFUSED  │
│        (Rcode 5) │
└─────────────────┘

5.2 Why Block Zone Transfers?

  • Reconnaissance: AXFR reveals all hostnames, subdomains, and internal IPs in a zone
  • Information leakage: Internal naming conventions, server names, service records (SRV), text records (TXT)
  • Attack surface mapping: Attackers use zone data to identify high-value targets
  • Principle: Zone transfers should only occur between authorized primary/secondary nameservers, never from client queries
Attacks blocked: Zone Transfer (AXFR/IXFR) — full reconnaissance prevention. Blocked

7. Stage 4: DNS Tunneling Detection (Entropy)

DNS tunneling encodes data inside subdomain labels (e.g., MFRA2YTKOJQWY2LT.attacker.com). DAD detects this by calculating the Shannon entropy of each subdomain label. High entropy + long labels = encoded data being smuggled through DNS.

7.1 Entropy Calculation Data Flow

Query: "MFRA2YTKOJQWY2LT.attacker.com"
         │
         ▼
┌─────────────────────────────────────────────┐
│  1. Split domain into labels                 │
│     labels = ["MFRA2YTKOJQWY2LT",            │
│               "attacker", "com"]             │
│                                              │
│  2. Identify subdomain labels                │
│     subdomain = labels[0..n-2]               │
│     = ["MFRA2YTKOJQWY2LT"]                   │
│                                              │
│  3. Check CDN whitelist                      │
│     suffix = "attacker.com"                  │
│     cdn_whitelist["attacker.com"]? → NO      │
│     (if YES → skip, legitimate high-entropy) │
│                                              │
│  4. For each subdomain label:                │
│     if len(label) >= min_label_length (12):  │
│       entropy = shannonEntropy(label)        │
│                                              │
│  5. Shannon Entropy of "MFRA2YTKOJQWY2LT":  │
│     M:1, F:1, R:1, A:2, 2:2, Y:2,            │
│     T:1, K:1, O:1, J:1, Q:1, W:1, L:1        │
│     H = -Σ p(x) * log2(p(x))                 │
│     p(A) = 2/16 = 0.125 → -0.125 * -3 = 0.375│
│     p(M) = 1/16 = 0.0625 → -0.0625*-4= 0.25  │
│     ... (sum all)                             │
│     H ≈ 3.82 bits/character                  │
│                                              │
│  6. Compare: 3.82 > threshold (3.5)?         │
│     YES → TUNNELING DETECTED → BLOCK         │
└─────────────────────────────────────────────┘

7.2 Shannon Entropy Formula

H(X) = - Σ p(xᵢ) · log₂(p(xᵢ))

Where:
  X = the string (subdomain label)
  xᵢ = each unique character in the string
  p(xᵢ) = frequency(xᵢ) / length(string)

Example: "AAAA" → H = 0.0 (no randomness)
         "ABCD" → H = 2.0 (moderate)
         "MFRA2YTKOJQWY2LT" → H ≈ 3.82 (high — encoded data)
         "www" → H = 1.58 (low — normal subdomain)

8. Stage 5: DGA Domain Detection

Domain Generation Algorithms produce pseudo-random domains for malware C2. DAD uses a multi-factor scoring system combining entropy, consonant ratio, digit ratio, and vowel absence to detect DGA domains.

8.1 Scoring Pipeline

Query: "xkjhsdf8923jksdf.com"
         │
         ▼
┌──────────────────────────────────────────────┐
│  1. Extract apex domain (eSLD)                │
│     labels = ["xkjhsdf8923jksdf", "com"]      │
│     apex = "xkjhsdf8923jksdf"                 │
│                                               │
│  2. Check minimum length (>= 8)               │
│     len("xkjhsdf8923jksdf") = 17 → OK         │
│                                               │
│  3. Calculate features:                       │
│     ┌──────────────────────────────────────┐  │
│     │ Shannon entropy:                     │  │
│     │   H("xkjhsdf8923jksdf") ≈ 3.71      │  │
│     │   threshold = 3.0 → +0.4 to score   │  │
│     │                                      │  │
│     │ Consonant ratio:                     │  │
│     │   consonants=13, letters=15          │  │
│     │   ratio = 13/15 = 0.87               │  │
│     │   threshold = 0.7 → +0.3 to score   │  │
│     │                                      │  │
│     │ Digit ratio:                         │  │
│     │   digits=4, total=17                 │  │

│     │                                      │  │

│     │                                      │  │

│     │ BLOCK_THRESHOLD = 0.5                │  │

│     └──────────────────────────────────────┘  │
└──────────────────────────────────────────────┘

9. Stage 6: C2 / Fast-Flux Detection

Fast-flux DNS rapidly rotates IP addresses for a domain using very short TTLs and botnet nodes as proxies. DAD tracks per-domain IP diversity and TTL volatility to detect this pattern.

12. Stage 9: DNSSEC Validation (Cache Poisoning)

DNSSEC (DNS Security Extensions) adds cryptographic signatures to DNS records. DAD validates the Authenticated Data (AD) flag in upstream responses. If validation fails and reject_bogus is enabled, the response is dropped — preventing cache poisoning attacks.

12.1 DNSSEC Validation Flow

┌──────────────────────────────────────────────────────────┐
│  Upstream response received from DoH server                │
│                                                            │
│  1. Check: resp.Rcode == RcodeSuccess (0)?                 │
│     If not → pass through (error responses don't need      │
│     DNSSEC validation)                                     │
│                                                            │
│  2. Check: resp.AuthenticatedData (AD bit)?                │
│     ┌────────────────────────────────────────────┐         │
│     │  AD bit = 1                                 │         │
│     │  → Upstream resolver validated DNSSEC       │         │
│     │  → Response is cryptographically verified   │         │
│     │  → PASS — continue to rebinding check       │         │
│     │                                             │         │
│     │  AD bit = 0                                 │         │
│     │  → Response NOT DNSSEC-validated            │         │
│     │  → If reject_bogus == true:                 │         │
│     │    → BLOCK — return SERVFAIL                │         │
│     │    → Alert: "DNSSEC validation failed -     │         │
│     │      possible cache poisoning"              │         │
│     │  → If reject_bogus == false:                │         │
│     │    → PASS (log warning only)                │         │
│     └────────────────────────────────────────────┘         │
└──────────────────────────────────────────────────────────┘

12.2 How DNSSEC Prevents Cache Poisoning

  Normal DNS (no DNSSEC):
  ─────────────────────────
  Attacker → forged response: "google.com → 6.6.6.6"
  Resolver → caches it → all users redirected to attacker

  DNSSEC-enabled:
  ─────────────────────────
  Attacker → forged response: "google.com → 6.6.6.6"
  Resolver → checks RRSIG signature against DNSKEY
           → signature doesn't match → REJECT
           → returns SERVFAIL
           → users protected

  Chain of trust:
  Root (.) ──DS──▶ TLD (.com) ──DS──▶ google.com
    │                  │                   │
  DNSKEY            DNSKEY              DNSKEY
  + RRSIG           + RRSIG             + RRSIG
  (signed by        (signed by          (signed by
   root key)         .com key)          google.com key)

  Each level signs the next. Forging requires breaking
  the cryptographic chain — computationally infeasible.

13. Stage 10: DNS Rebinding Protection

DNS rebinding exploits the browser's same-origin policy. An attacker-controlled domain first resolves to a public IP, then after TTL expiry, resolves to an internal RFC1918 address. The attacker's JavaScript can then access internal network resources through the victim's browser.

13.1 Rebinding Attack (Without Protection)

  Time T=0: Browser visits evil.attacker.com
  ─────────────────────────────────────────────
  DNS Query: evil.attacker.com → A record
  DNS Response: evil.attacker.com → 93.184.216.34 (public IP)
  Browser loads page from 93.184.216.34
  JavaScript begins executing...

  Time T=60 (TTL expires):
  ─────────────────────────────────────────────
  JavaScript triggers new DNS lookup for evil.attacker.com
  DNS Response: evil.attacker.com → 192.168.1.1 (PRIVATE IP!)
  Browser same-origin policy: evil.attacker.com == evil.attacker.com ✓
  JavaScript can now make requests to 192.168.1.1 (router admin panel)
  → Exfiltrates router credentials, internal service data, etc.

13.2 DAD Rebinding Protection Flow

┌──────────────────────────────────────────────────────────┐

    → Passes all stages → upstream resolves to 93.184.216.34 (public)
    → DNSSEC valid (AD=1) → no rebinding (public IP) → cached, returned

  Time T=61 (TTL=60 expires): Query "evil.rebind.com" type A
    → Cache expired, forward to upstream
    → Attacker's DNS returns: 192.168.1.1 (ROUTER IP!)
    → Stage 9 (DNSSEC): AD=1 (attacker has valid DNSSEC for their domain)
    → Stage 10 (Rebinding):
      Answer record: A 192.168.1.1
      IsPrivateIP("192.168.1.1") → check 192.168.0.0/16 → MATCH!
      ✅ BLOCKED → NXDOMAIN returned
      ✅ Alert: {type: "dns_rebinding", severity: "critical",
                 message: "public domain resolving to private IP"}
      Browser never sees 192.168.1.1 → JavaScript cannot access router

17.4 Scenario: NXDOMAIN Water Torture

ATTACK: Botnet floods resolver with random subdomains of target domain
  Queries: "a1x2y3.target.com", "b4c5d6.target.com", "e7f8g9.target.com", ...

  Query 1-10: Pass all stages, upstream returns NXDOMAIN
    → NXDOMAIN bucket: 10→9→8→...→1→0
    → Each NXDOMAIN cached for negative_ttl (60s)

  Query 11: "k2p9q8.target.com"
    Stage 1 (Rate Limit):
      nxdomain_tokens = 0 < 1.0
      ✅ BLOCKED → packet dropped
      ✅ Alert: {type: "rate_limit", severity: "warn"}
    → No upstream query → target DNS server protected from flood

17.5 Scenario: Cache Poisoning Attempt

ATTACK: On-path attacker injects forged DNS response for "bank.com"
  (DAD uses DoH, so attacker cannot see/inject — but if DoH disabled:)

  Plain DNS mode: Attacker sends forged response: bank.com → 6.6.6.6
  DAD receives response from upstream (or attacker's forged packet)
  Stage 9 (DNSSEC):
    resp.AuthenticatedData = false (forged response has no valid RRSIG)
    reject_bogus = true
    ✅ BLOCKED → SERVFAIL returned to client
    ✅ Alert: {type: "dnssec_validation_fail", severity: "critical",
               message: "DNSSEC validation failed - possible cache poisoning"}
    Client receives SERVFAIL → does not connect to attacker's IP

20. Appendix: Shannon Entropy Mathematics

20.1 Formula

H(X) = - Σᵢ p(xᵢ) · log₂(p(xᵢ))

Where:
  X  = random variable (string of characters)
  xᵢ = i-th unique character
  p(xᵢ) = count(xᵢ) / |X|   (probability of character xᵢ)
  H   = entropy in bits per character

Range:
  H = 0.0  → all characters identical (no randomness)
  H = log₂(n) → uniform distribution over n unique chars (max entropy)

For ASCII alphanumeric (a-z, A-Z, 0-9 = 62 chars):
  Max H = log₂(62) ≈ 5.95 bits/char

20.2 Worked Example: "ABCD"

String: "ABCD"
Length: 4
Unique chars: A, B, C, D (each appears once)

p(A) = 1/4 = 0.25
p(B) = 1/4 = 0.25
p(C) = 1/4 = 0.25
p(D) = 1/4 = 0.25

H = -[0.25·log₂(0.25)] × 4
  = -[0.25·(-2)] × 4
  = -[-0.5] × 4
  = 0.5 × 4
  = 2.0 bits/char

20.3 Worked Example: "MFRA2YTKOJQWY2LT"

String: "MFRA2YTKOJQWY2LT"
Length: 16
Unique chars and frequencies:
  M:1, F:1, R:1, A:2, 2:2, Y:2, T:1, K:1, O:1, J:1, Q:1, W:1, L:1

Characters appearing once (11 chars): p = 1/16 = 0.0625
  contribution per char: -0.0625 · log₂(0.0625) = -0.0625 · (-4) = 0.25
  total: 11 × 0.25 = 2.75

Characters appearing twice (3 chars: A, 2, Y): p = 2/16 = 0.125
  contribution per char: -0.125 · log₂(0.125) = -0.125 · (-3) = 0.375
  total: 3 × 0.375 = 1.125

H = 2.75 + 1.125 = 3.875 ≈ 3.88 bits/char

This exceeds DAD's threshold of 3.5 → flagged as DNS tunneling.

20.5 Consonant Ratio Calculation

consonantRatio(s) = consonantCount / letterCount

Vowels: a, e, i, o, u (case-insensitive)
Consonants: all other letters
Non-letters (digits, hyphens) are excluded from both counts

Example: "xkjhsdf8923jksdf"
  Letters: x,k,j,h,s,d,f,j,k,s,d,f = 12 letters
  Consonants: all 12 (no vowels)
  Ratio: 12/12 = 1.0 → very high (DGA indicator)

Example: "google"
  Letters: g,o,o,g,l,e = 6 letters
  Consonants: g,g,l = 3
  Ratio: 3/6 = 0.50 → normal
