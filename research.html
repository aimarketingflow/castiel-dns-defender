1. DNS Threat Landscape & Attack Taxonomy

DNS is both a critical service target and a weapon. Attacks fall into five categories:

CategoryGoalAttack TypesTag
Volumetric / DDoSOverwhelm DNS infraDNS Amplification, Water Torture (Random Subdomain), NXDOMAIN FloodVolumetric
InterceptionRedirect usersCache Poisoning, DNS Hijacking, Subdomain Takeover, DNS Rebinding, On-Path MITMIntercept
ExfiltrationSmuggle data outDNS Tunneling (iodine, dnscat2), Slow-drip exfil, C2 over DNS, DoH abuseExfiltration
ReconnaissanceMap infrastructureZone Transfers (AXFR), Zone Walking (NSEC), Subdomain EnumerationRecon
EvasionHide malicious infraFast Flux DNS, Domain Generation Algorithms (DGA), Dynamic DNS abuseEvasion

1.1 Key Attack Details

DNS Cache Poisoning

Injects forged responses into resolver cache → attacker-controlled IPs for legitimate domains. Persists until TTL expiry. Mitigated by source-port randomization, 0x20 case encoding, DNSSEC.

DNS Amplification DDoS

Spoofed-source queries to open resolvers → large responses (ANY, DNSSEC) reflected to victim. 50–70× amplification. Mitigated by RRL, BCP38, disabling open recursion.

Water Torture / Random Subdomain

Floods authoritative servers with queries for random non-existent subdomains (a8k3m2.example.com). Each forces full lookup + NXDOMAIN. Unique queries defeat caching.

DNS Tunneling

Encodes data in DNS queries/responses (TXT, CNAME, NULL records). Port 53 universally allowed through firewalls → C2, exfiltration, VPN tunnels. Detection: Shannon entropy analysis, query length heuristics, subdomain fan-out tracking.

DNS Hijacking

Control of DNS resolution via compromised registrar/NS config. Targets authoritative side, unlike cache poisoning. Mitigated by registrar locks, DNSSEC, monitoring for unexpected NS changes.

DNS Rebinding

Attacker domain initially resolves to public IP, then after TTL to internal IP (192.168.1.1) → JS accesses internal resources via browser same-origin bypass. Mitigated by blocking public FQDNs resolving to RFC1918.

Fast Flux DNS

Rapid IP rotation with short TTLs. Single-flux: A/AAAA rotation. Double-flux: also rotates NS records. Detected via TTL volatility + ASN diversity analysis.

Domain Generation Algorithms (DGA)

Malware generates pseudo-random domains algorithmically. Only attacker knows active domain. Detected via entropy analysis, consonant ratios, ML classifiers (n-gram models).

Sources: FIRST DNS Abuse Techniques Matrix v1.3 · MITRE ATT&CK T1568, T1498/002 · CAPEC-142, CAPEC-275

4. Network IDS with DNS Capabilities

Full network intrusion detection systems that include robust DNS protocol analysis.

Suricata C
High-performance NIDS/NIPS/NSM engine. Extensive DNS keyword support: dns.query, dns.answers.rrname, dns.response, dns.opcode. Supports multi-buffer matching on all DNS sections. Signature-based + protocol anomaly detection.
OISF / Foundation-backedMulti-threadedEVE JSON loggingLua scripting
  • Sticky buffers for query names, answer names, authority, additional sections
  • Can match on DNS response codes, opcodes, and flags
  • Integrates with ELK, Splunk, Wazuh for alerting
  • Community + ET Pro rulesets include DNS-specific signatures
Zeek (formerly Bro) C++
Network analysis framework with deep DNS protocol parsing. Generates structured dns.log with query/response correlation, EDNS, DNSSEC fields. Scriptable policy engine for custom detectors.
NSF-fundedScripting languageCluster modeIntel framework
  • Events: dns_request, dns_message, dns_query_reply, dns_AAAA_reply, etc.
  • Built-in correlation of queries with responses via transaction ID
  • Intel framework for IOC matching against DNS queries
  • Packages: dns-tunneling, domain-dga, dns-axfr detection
Key insight: Suricata excels at signature-based inline blocking; Zeek excels at structured logging, correlation, and custom scripted analysis. Many production deployments run both side by side — Suricata for real-time blocking, Zeek for deep forensics and anomaly hunting.

8. Rate Limiting & DDoS Mitigation

Tools and techniques specifically targeting volumetric DNS attacks.

dnsdist C++ Lua
DNS-aware load balancer and DDoS shield by PowerDNS. Lua-scriptable policy engine for real-time traffic shaping. DoH/DoT/DoQ/DoH3 termination. Per-IP QPS limiting, regex rules, TC-forcing for UDP floods.
PowerDNS projectHundreds of millions of usersPrometheus + Carbon metrics

Key DDoS Capabilities

  • MaxQPSIPRule(N) — per-IP/subnet rate limiting with configurable action (drop, delay, TC=1)
  • MaxQPSRule(N) — global QPS ceiling
  • RegexRule() — pattern-based blocking (e.g., random subdomain patterns)
  • QNameSuffixRule() — efficient domain list matching
  • TC=1 forcing sends UDP clients to TCP (raises attacker cost)
  • Dynamic rule management via runtime console
CoreDNS RRL Plugin Go
BIND-like Response Rate Limiting for CoreDNS. Token-bucket accounting per response category (positive, NODATA, NXDOMAIN, referrals, errors). Slip-ratio for legitimate fallback. Wildcard flooding protection via metadata plugin.
CoreDNS pluginBIND9-compatible behaviorReport-only mode

Configuration Options

  • responses-per-second — positive response allowance
  • nxdomains-per-second — NXDOMAIN response allowance
  • errors-per-second — error response allowance
  • slip-ratio N — let every Nth rate-limited response through (TC=1) for legitimate client recovery
  • report-only — log without enforcing, for tuning
BIND 9 RRL (built-in)
Native Response Rate Limiting in BIND 9.10+. Credit/token-bucket scheme per response category + client prefix. Configurable in named.conf options or view blocks. Large authoritative operators report huge traffic reductions.
Built into BINDISC maintainedlog-only mode for tuning
  • 15-second rolling window (configurable 1–3600s)
  • Per-category: responses-per-second, nxdomains-per-second, errors-per-second, all-per-second
  • qps-scale — dynamic scaling based on total query rate
  • Recommended for authoritative servers (higher false-positive risk on recursive)
Note: RRL is designed for authoritative servers to prevent amplification abuse. For recursive resolvers, access control (ACLs) + dnsdist as a front-end proxy is the preferred mitigation approach.

10.3 Real-Time Alerting Pipeline

For the "alert in real time" requirement, the recommended pipeline is:

  1. dnsdist handles wire-speed rate limiting and drops obvious volumetric attacks inline
  2. DNS-collector streams enriched DNS events to Prometheus (metrics) and Loki (logs)
  3. Grafana evaluates alert rules on Prometheus metrics (QPS spikes, NXDOMAIN ratios, entropy anomalies)
  4. Suricata generates EVE JSON alerts for signature matches → forwarded to SIEM
  5. ML Engine (dnsxray or custom) processes Zeek logs / Kafka stream for behavioral anomalies
  6. Alert routing: Grafana → PagerDuty / Slack / Email / Webhook for human response

11.1 Recommended MVP Stack

For a minimum viable DNS Attack Defender deployment:

  1. dnsdist — front-end load balancer with rate limiting (stops volumetric attacks)
  2. Unbound — validating recursive resolver with DNSSEC (stops cache poisoning)
  3. dnsink or Dgaard — threat-intel-driven blocking + tunneling detection
  4. DNS-collector — DNStap telemetry to Prometheus + Loki
  5. Grafana — dashboards + real-time alerting (Slack/email/PagerDuty)

11.2 Advanced Add-ons

  • Zeek — deep DNS protocol logging + custom detection scripts
  • Suricata — inline IPS with ET Pro rulesets for known attack signatures
  • dnsxray / custom ML — behavioral anomaly detection for DGA, fast flux, C2
  • UDPot — honeypot on unused IPs for early warning intelligence
  • PassiveDNS — historical DNS record database for forensic investigations

11.3 Key Design Principles

  • Defense in depth: No single tool covers all attack types — layer multiple tools
  • Inline + passive: Rate limiting and blocking inline; deep analysis on mirrored traffic
  • Threat intel freshness: Auto-refresh feeds hourly minimum (URLhaus, PhishTank, Abuse.ch)
  • False positive management: Start in report-only / log-only mode, tune thresholds, then enforce
  • Encrypted DNS: Use DoH/DoT upstream to prevent on-path manipulation of resolver queries
  • DNSSEC everywhere: Validate on resolvers to prevent cache poisoning at the crypto layer
  • Observability first: You can't defend what you can't see — comprehensive DNS logging is foundational

11.4 Next Steps for This Project

  1. Choose target deployment environment (home lab, SME, enterprise, ISP)
  2. Deploy MVP stack (dnsdist + Unbound + dnsink + DNS-collector + Grafana)
  3. Integrate threat intelligence feeds and tune detection thresholds
  4. Add ML detection layer (dnsxray or custom model trained on local traffic)
  5. Build custom alerting rules in Grafana tied to Slack / PagerDuty
  6. Deploy honeypot (UDPot) on unused network addresses for early warning
  7. Establish baseline metrics and iteratively reduce false positives
