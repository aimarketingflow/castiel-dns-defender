LuLu & Castiel — Interaction Analysis

How two macOS network tools conflict and what breaks

August 2026 · macOS Tahoe (Apple Silicon M1) · Castiel v1.1.1 · LuLu 4.2.1

Executive Summary

Castiel uses macOS's BSD Packet Filter (pfctl) to redirect DNS traffic from port 53 to a local proxy on port 5300. LuLu uses Apple's Network Extension framework (NEFilterDataProvider) to intercept and filter all outbound socket connections at the application layer. These two mechanisms operate at different layers of the networking stack and interact in ways that can break DNS resolution, kill DoH connections, and cause the WiFi ! symbol.

The core problem: Apple's Network Extension framework intercepts ALL network flows before they reach PF, and there is no way for LuLu to "bypass" traffic — even when "Allow DNS Traffic" is enabled, macOS still delivers every packet to LuLu for inspection. This adds latency, can kill TLS handshakes to DoH endpoints, and creates race conditions between the two tools.

How Each Tool Works

Castiel — PF-Based DNS Interception

Castiel operates at the packet layer using macOS's built-in PF (Packet Filter) firewall. It installs a PF anchor with rdr rules that redirect all DNS traffic (port 53) to a local proxy on port 5300: 

rdr pass on lo0 inet proto udp from any to any port 53 -> 127.0.0.1 port 5300
rdr pass on lo0 inet proto tcp from any to any port 53 -> 127.0.0.1 port 5300

PF operates below the application layer — it sees packets after they've been routed but before they leave the network interface. Castiel also blocks direct DoH/DoT connections to known public resolvers (port 443/853 to IPs like 1.1.1.1, 8.8.8.8, etc.) to prevent DNS traffic from bypassing its proxy.

Note: Apple has stated in TN3165 that "Packet Filter is not API" and recommends Network Extension providers instead. However, PF remains the only way to do transparent DNS redirection without a System Extension, and is used by Mullvad VPN, IVPN, and others.

LuLu — Network Extension Socket Filter

LuLu operates at the application/socket layer using Apple's Network Extension framework. It registers as a NEFilterDataProvider — a System Extension that intercepts every outbound socket connection before it reaches the network stack. For each new flow, LuLu applies a verdict: allow or block.

Critically, macOS delivers ALL network traffic to LuLu — there is no way to bypass the Network Extension framework. Even with "Allow DNS Traffic" enabled, macOS still passes DNS flows to LuLu for inspection. LuLu then explicitly allows them, but the inspection adds 20-25ms latency to every UDP DNS query.

LuLu's System Extension (com.objective-see.lulu.extension) runs as a separate process that stays loaded even when the LuLu UI is disabled. Disabling LuLu in the menu bar stops new alerts but the Network Extension remains [activated enabled] until fully deactivated in System Settings or removed via systemextensionsctl.

The Packet Processing Order

According to Apple's Developer Forums, the order of processing on macOS is: 

┌─────────────────────────────────────────────────────────────┐
│                    Application Process                       │
│                         │                                    │
│                         ▼                                    │
│  ┌─────────────────────────────────────────────────────┐    │
│  │  1. NEFilterDataProvider (LuLu's Socket Filter)     │    │
│  │     • Intercepts every new socket flow              │    │
│  │     • Applies allow/block verdict                   │    │
│  │     • Can see URL (Network.framework) or IP:port     │    │
│  │     • "Allow DNS Traffic" = auto-allow UDP/53       │    │
│  └────────────────────┬────────────────────────────────┘    │
│                       │ (allowed flows continue)            │
│                       ▼                                      │
│  ┌─────────────────────────────────────────────────────┐    │
│  │  2. DNS Proxy (if any NEDNSProxyProvider running)   │    │
│  │     • Only one DNS proxy can run at a time          │    │

│  └────────────────────┬────────────────────────────────┘    │

│  │  3. VPN (NEPacketTunnelProvider)                    │    │

│  └────────────────────┬────────────────────────────────┘    │
│                       ▼                                      │
│  ┌─────────────────────────────────────────────────────┐    │

│  │     • block out to known DoH resolver IPs           │    │
│  └────────────────────┬────────────────────────────────┘    │
│                       ▼                                      │
│              Network Interface (en0/lo0)                     │
└─────────────────────────────────────────────────────────────┘

LuLu sees traffic first, PF sees it last. This ordering creates several specific conflicts.

Identified Conflicts

Conflict 1: DoH (HTTPS to Cloudflare DNS) Killed Mid-TLS Critical

Symptom: Castiel's DoH health check fails with read: socket is not connected. The TCP connection to cloudflare-dns.com:443 establishes but is killed during the TLS handshake.

Root cause: LuLu's Network Extension intercepts the HTTPS connection to Cloudflare's DoH endpoint. The flow appears as a TCP connection to 104.16.249.249:443. LuLu's "Allow DNS Traffic" setting only auto-allows UDP port 53 — it does NOT cover HTTPS on port 443 to DNS resolver IPs. If LuLu has no explicit allow rule for castiel or for Cloudflare's IPs on port 443, it may block or delay the connection. The TLS handshake gets killed mid-stream, producing the "socket is not connected" error (POSIX error 57, ENOTCONN).

Why "Allow DNS Traffic" doesn't help: That setting only auto-allows UDP/53. DoH uses HTTPS (TCP/443), which LuLu treats as a regular HTTPS connection — subject to normal rule evaluation. The LuLu source code explicitly checks for IPPROTO_UDP and port 53:

//check proto (UDP) and port (53)
if( (IPPROTO_UDP == ((NEFilterSocketFlow*)flow).socketProtocol) &&
    (YES == [((NWHostEndpoint*)((NEFilterSocketFlow*)flow).remoteEndpoint).port isEqualToString:@"53"]) ) {
    //allow
    verdict = [NEFilterNewFlowVerdict allowVerdict];
}

No equivalent exists for TCP port 443 to DNS resolver IPs.

Impact on Castiel: DoH fails, Castiel falls back to plain DNS (still functional but unencrypted). The castiel_doh_enabled metric may show 0. DoH health check logs fill with errors every 30 seconds.

Fix Options

  • Best: Disable LuLu entirely and reboot (unloads the System Extension)
  • Alternative: Add a LuLu allow rule for /usr/local/bin/castiel (process-based, allows all its connections)
  • Alternative: Add LuLu allow rules for 104.16.249.249:443 and 104.16.248.249:443 (remote endpoint-based)
  • Workaround: Disable DoH in Castiel config (use_doh: false) — plain DNS still works through PF redirect

Conflict 2: Orphaned PF Rules Break All DNS Critical

Symptom: WiFi shows ! exclamation mark. No DNS resolution. Internet completely broken.

Root cause: Castiel's PF redirect rules remain active even when the Castiel daemon is not running. If Castiel crashes or is stopped by launchd, the PF anchor still redirects port 53 → port 5300, but nothing is listening on 5300. Every DNS query goes into a void.

How LuLu makes this worse: LuLu's Network Extension can cause Castiel to crash indirectly. When LuLu kills DoH connections repeatedly, the DoH health checker logs continuous failures. If this triggers a panic or resource exhaustion in the Go runtime, Castiel exits — but PF rules stay. LuLu itself isn't broken, but its interference with DoH creates the conditions for Castiel to crash.

Timeline of the incident we experienced:

  1. Castiel running with PF redirect + DoH enabled
  2. LuLu's Network Extension kills DoH TLS handshakes repeatedly
  3. Castiel daemon exits (received SIGTERM from launchd during a restart cycle)
  4. PF rules remain — port 53 still redirects to 5300
  5. Nothing listening on 5300 → all DNS fails → WiFi shows !

Fix (already implemented in v1.1.1):

  • All exit paths (crash, panic, SIGTERM, SIGINT) now explicitly call fwMgr.Cleanup() before os.Exit()
  • pf.Cleanup() flushes both NAT/rdr and filter rules, then removes the anchor
  • launchd plist uses KeepAlive: true to auto-restart within 5 seconds

Conflict 3: UDP DNS Latency Penalty Moderate

Symptom: DNS queries through Castiel are 20-25ms slower than expected.

Root cause: Even with "Allow DNS Traffic" enabled in LuLu, macOS's Network Extension framework still delivers every UDP DNS flow to LuLu for inspection. LuLu immediately returns an "allow" verdict, but the round-trip through the Network Extension adds 20-25ms. This is a fundamental limitation of Apple's framework — there is no way to bypass it.

As confirmed by LuLu's developer in GitHub Issue #832:

"The way macOS's Network Extension framework works is that it delivers all network traffic to LuLu. So even with this option enabled, macOS will still pass the traffic to LuLu (there's no way around that). However, LuLu can then explicitly allow that traffic."

Impact on Castiel: DNS queries that should take 3-7ms (LAN) now take 23-32ms. Not breaking, but degrading performance — especially for DNS-heavy workloads. The latency is visible in dig output and in the castiel_query_duration_seconds Prometheus metric.

Fix: Only way to eliminate this latency is to fully disable LuLu's Network Extension (not just toggle it off in the UI — requires deactivation in System Settings or reboot).

Conflict 4: Castiel's DoH Block Rules vs. LuLu's Allow Rules Moderate

Symptom: Applications that try to use DoH directly (e.g., Chrome's built-in DoH) fail, but LuLu shows them as "allowed".

Root cause: Castiel installs PF block rules for known DoH resolver IPs (1.1.1.1, 8.8.8.8, etc.) on ports 443 and 853. This is intentional — it prevents apps from bypassing Castiel's DNS filtering. However, LuLu may have allow rules for these same IPs (e.g., if the user allowed Chrome's connections). LuLu's allow verdict lets the flow through the socket filter, but PF then blocks it at the packet layer.

This creates a confusing user experience: LuLu says "allowed" but the connection fails. The user may blame LuLu when Castiel is actually responsible.

Fix: No fix needed — this is by design. Castiel's PF rules are intentionally more restrictive than LuLu's socket filter rules. Document this behavior for users.

Conflict 5: LuLu Network Extension Stays Active When "Disabled" Critical

Symptom: Disabling LuLu in the menu bar UI does not restore DoH connectivity. The ! WiFi symbol persists.

Root cause: LuLu's UI "disable" only stops showing alerts and applying new rules. The underlying System Extension (com.objective-see.lulu.extension) remains [activated enabled] in the system. The Network Extension continues intercepting all flows. This is by design in Apple's Network Extension framework — the extension stays loaded until explicitly deactivated.

Verification command:

$ systemextensionsctl list
* * VBG97UB4TA com.objective-see.lulu.extension (4.2.1/4.2.1) LuLu [activated enabled]

$ sudo launchctl list | grep lulu
- 0 NetworkExtension.com.objective-see.lulu.extension.4.2.1.4.2.1

Even when the LuLu UI shows "disabled", the extension process may still be running and intercepting traffic.

Fix:

  1. Go to System Settings → General → Login Items & Extensions → Network Extensions
  2. Click the (i) button next to Network Extensions
  3. Toggle LuLu to Off
  4. Reboot — the System Extension is only fully unloaded after a reboot

Alternatively, remove the extension entirely:

sudo systemextensionsctl reset

Conflict 6: NEFilterDataProvider and NEDNSSettings Are Mutually Exclusive Architecture Limitation

Symptom: macOS system-level DoH/DoT profiles (e.g., NextDNS, Quad9) cannot be activated while LuLu is running.

Root cause: Apple's NEFilterDataProvider (LuLu) and NEDNSSettings (system DoH/DoT profiles) are mutually exclusive on macOS (radar 64940244). When a NEFilterDataProvider is active, it takes precedence over DNS Settings. This is an Apple limitation, not a LuLu bug.

Impact on Castiel: This doesn't directly affect Castiel (which implements its own DoH in Go, not via system profiles). But it means users cannot use macOS's native DoH support alongside LuLu. Castiel's Go-based DoH is a workaround for this limitation — it makes HTTPS connections directly, bypassing the system DNS stack entirely. However, LuLu's socket filter still intercepts those HTTPS connections (see Conflict 1).

Conflict 7: Multiple Network Extensions Conflict Known macOS Bug

Symptom: WiFi ! symbol, no internet, DNS failures when both LuLu and another Network Extension (VPN, Cisco AnyConnect, etc.) are active.

Root cause: macOS has well-documented bugs when multiple Network Extensions are active simultaneously. Apple's Developer Forums confirm that socket filters from different vendors can conflict, causing connections to drop, DNS to fail, and ping to stop working. This has been reported with LuLu + Cisco AnyConnect, LuLu + TripMode, LuLu + Radio Silence, and LuLu + Avast.

From LuLu Issue #355:

"If Lulu is enabled, when I connect to WiFi it either comes up with ! symbol over WiFi icon, or it does connect but then Internet is basically inaccessible. I'm pretty sure it's due to DNS lookups being blocked."

Impact on Castiel: Castiel doesn't use a Network Extension (it uses PF), so it doesn't directly conflict with LuLu at the NE level. However, if a VPN (ProtonVPN) is also running, the combination of LuLu (NE) + ProtonVPN (NE) + Castiel (PF) creates a three-way interaction where DNS traffic is intercepted by LuLu, routed through the VPN tunnel, and then redirected by PF — and any failure at any stage breaks everything.

Recommended Coexistence Strategy

For the Gatebreaker Test Campaign

The simplest and most reliable approach:

  1. Disable LuLu completely — System Settings → Login Items & Extensions → Network Extensions → LuLu → Off
  2. Reboot — This fully unloads the System Extension
  3. Disable ProtonVPN — VPN + PF + NE is a three-way conflict
  4. Start Castiel — sudo launchctl start com.castiel.daemon
  5. Verify: dig @127.0.0.1 -p 5300 google.com +short returns an IP
  6. Verify: curl -s http://127.0.0.1:9090/metrics | grep doh_enabled shows 1

For Long-Term Production Use

If LuLu and Castiel must coexist:

  1. Add a LuLu allow rule for /usr/local/bin/castiel — This allows all of Castiel's outbound connections (DoH to Cloudflare, plain DNS to upstreams) without per-IP rules
  2. Disable DoH in Castiel — Set use_doh: false in config. Plain DNS through PF redirect works fine with LuLu (just 20-25ms slower). DoH over HTTPS is where the conflicts happen.
  3. Accept the 20-25ms latency penalty — LuLu's Network Extension will inspect every DNS flow. This is unavoidable.
  4. Monitor for orphaned PF rules — If WiFi breaks, check sudo pfctl -a castiel -s rules first. The v1.1.1 cleanup fixes should prevent this, but monitoring is prudent.
  5. Do not run ProtonVPN simultaneously — Three network-layer tools (LuLu NE + ProtonVPN NE + Castiel PF) is asking for trouble.

Why Not Migrate Castiel to Network Extension?

Apple's TN3165 explicitly recommends moving away from PF to Network Extension providers. However, this creates new problems for Castiel:

Aspect PF (Current) Network Extension
DNS Redirect Simple rdr rule Requires NEDNSProxyProvider or NETransparentProxyProvider
Coexistence with LuLu PF sees traffic after LuLu — some conflicts Only one DNS proxy at a time; mutually exclusive with LuLu's filter
Code signing Standard Developer ID Requires com.apple.developer.networking.networkextension entitlement from Apple
System Extension approval Not needed User must approve multiple System Extension dialogs
DoH support Castiel implements its own Go DoH client NEDNSSettings is mutually exclusive with NEFilterDataProvider
Root access Yes (can modify PF rules) No (System Extension runs non-root, controlled by OS)
Reliability PF is kernel-level, very reliable Network Extension framework has known bugs (Tahoe attachment issues, multiple NE conflicts)

Conclusion: Migrating to Network Extension would make Castiel less compatible with LuLu, not more. The NEDNSProxyProvider is mutually exclusive with LuLu's NEFilterDataProvider — only one can run at a time. Castiel's current PF-based approach is actually the most compatible option for coexistence with Network Extension-based tools like LuLu.

Mullvad VPN and IVPN have reached the same conclusion — they continue using PF despite Apple's recommendation, because Network Extension doesn't provide the control they need and has reliability issues.

Known LuLu Bugs on macOS Tahoe

From LuLu Issue #825, LuLu 4.2.1 has a specific incompatibility with macOS Tahoe:

  • Network Extension installs but never attaches (refcount stays 0)
  • Provider process never starts
  • LuLu UI never appears (no menu bar icon)
  • No connection prompts are shown
  • System Settings shows LuLu as "Enabled" but it's non-functional

This means on Tahoe, LuLu may appear to be running but not actually filtering anything — or worse, it may be in a half-attached state that interferes with network traffic without providing any filtering benefit. If you see LuLu in System Settings but no menu bar icon, it's in this broken state.

Check with:

$ systemextensionsctl list | grep lulu
$ sudo launchctl list | grep lulu
$ ps aux | grep com.objective-see.lulu.extension

If refcount is 0 or the process isn't running, LuLu is non-functional on Tahoe and should be removed:

sudo systemextensionsctl reset
