Stealth Connectivity

Defensive use of macOS captive portal state as a network security mechanism

August 2026 · Research Report · Castiel DNS Defender

Executive Summary

When macOS's captive portal probe fails, the OS enters a "limited connectivity" state — the WiFi icon shows !, NWPathMonitor reports .unsatisfied, and the system believes there is no internet connection. But if DNS and routing still work through a local proxy like Castiel, all traffic flows normally while macOS and its applications think they're offline.

This creates an accidental "stealth mode" where:

  • Well-behaved applications defer network activity (reducing noise and attack surface)
  • Malware performing connectivity checks (MITRE ATT&CK T1016.001) may conclude there's no internet and withhold payloads
  • Background sync services (iCloud, Dropbox, Slack) pause, reducing DNS chatter
  • Castiel still sees and filters all DNS traffic that does go through

This research explores whether this state can be intentionally induced and maintained as a defensive mechanism, examines the technical mechanisms involved, and evaluates the trade-offs.

How macOS Determines Internet Status

The Captive Portal Probe

macOS determines internet connectivity through a one-shot HTTP probe to Apple's captive portal detection endpoint. When a network interface comes up, mDNSResponder (the system DNS resolver) resolves captive.apple.com and issues an HTTP GET to: 

http://captive.apple.com/hotspot-detect.html

The expected response is a minimal HTML page containing the word "Success". If the response matches, macOS marks the network as having internet access. If the probe fails (timeout, wrong response, redirect, or DNS failure), macOS marks the network as captive or limited.

Apple also probes via HTTPS on port 443 to the same host, as documented in their enterprise network guide:

Host: captive.apple.com
Ports: 443, 80
Protocol: TCP
Description: Internet connectivity validation for networks that use captive portals

The Key Limitation: No Re-Probing

Critical finding: macOS performs the captive portal probe once during network association. If the probe fails, the ! status persists until the user toggles WiFi, reconnects to the network, or reboots. There is no automatic re-probe mechanism. This was confirmed through Apple Developer Forums and Mullvad VPN's engineering documentation.

This means: if Castiel's PF rules cause the captive probe to fail during startup (by redirecting DNS or blocking the probe host), the ! state will persist indefinitely — even after Castiel is fully operational and DNS works perfectly.

What the Probe Triggers

When the probe fails, macOS sets several internal state flags:

API Value Effect
NWPathMonitor .unsatisfied or .requiresConnection Apps see "no network"
SCNetworkReachability kSCNetworkReachabilityFlagsConnectionRequired Legacy apps see "connection required"

How Applications Respond to "No Internet"

Modern Apps: NWPathMonitor + URLSession

Since macOS 10.14 / iOS 12, Apple's recommended approach is NWPathMonitor for status monitoring and URLSession with waitsForConnectivity = true for network requests. When the path is .unsatisfied:

  • URLSession with waitsForConnectivity — The session waits and does not attempt the request. The task is queued but deferred until the path becomes .satisfied. This is Apple's recommended pattern, meaning most modern macOS apps will silently defer network activity.
  • URLSession without waitsForConnectivity — The task fails immediately with NSURLErrorNotConnectedToInternet (-1009).
  • NWConnection — Connection attempts fail or are delayed depending on configuration.

Apple's own guidance from Developer Forums:

"Don't use [NWPathMonitor] to prevent the user from attempting to perform a network operation, that is, don't 'preflight' your network connections... NWPathMonitor can generate both false positives and false negatives."

Despite this guidance, many apps do preflight with NWPathMonitor and skip network work when the path is .unsatisfied. This is especially common in:

  • Background sync services (iCloud, Dropbox, Google Drive, OneDrive)
  • Messaging apps (Slack, Teams, Discord) — presence/status updates
  • Auto-update mechanisms (Sparkle, macOS software update)
  • Telemetry/analytics SDKs
  • Push notification registration (APNs)

Legacy Apps: SCNetworkReachability

Older macOS apps and cross-platform frameworks (Qt, Electron) may use SCNetworkReachabilityGetFlags. When the captive probe fails, the kSCNetworkReachabilityFlagsConnectionRequired flag is set, causing these apps to believe a dial-up or VPN connection needs to be established first.

System Daemons

Apple's own system services also respond to the connectivity state:

  • mDNSResponder — May delay publishing DNS resolvers to scutil --dns until the captive probe completes
  • configd — Delays publishing the default route to the routing table until the probe succeeds or times out
  • softwareupdated — Won't check for macOS updates
  • cloudd — iCloud sync pauses
  • apsd — Push notification delivery may be delayed
  • photolibraryd — iCloud Photos sync pauses

Mullvad VPN documented this exact problem: "The default route is only published when macOS finishes or times out its captive portal check. The captive portal check involves looking up specific captive portal domains and issuing an HTTP request to the resolved address, and by default, if the app is blocking traffic, none of these network operations can take place, so the timeout is always incurred."

How Malware Responds to "No Internet"

This is where the defensive potential becomes most interesting. MITRE ATT&CK documents this as T1016.001 — Internet Connection Discovery:

"Adversaries may check for Internet connectivity on compromised systems. This may be performed during automated discovery and can be accomplished in numerous ways such as using Ping, tracert, and GET requests to websites, or performing initial speed testing to confirm bandwidth. Adversaries may use the results and responses from these requests to determine if the system is capable of communicating with their C2 servers before attempting to connect to them."

Common Connectivity Check Methods on macOS

  1. ping 8.8.8.8 — ICMP echo to Google DNS. This bypasses DNS but not PF. Castiel's PF rules don't block ICMP, so this would succeed.
  2. curl http://example.com — HTTP GET to a known site. Requires DNS, which goes through Castiel. Castiel can log and block this.
  3. scutil --nwi — Checks network reachability flags. Would report "Reachable" but may show no default route. Inconclusive.
  4. networksetup -getinfo Wi-Fi — Gets network config. Shows IP and router, doesn't test connectivity.
  5. getaddrinfo("google.com") — DNS resolution check. Goes through Castiel. Succeeds because Castiel resolves it.
  6. InternetCheckConnection / WinHttpConnect — Windows APIs, not relevant on macOS.
  7. Raw socket connect to hard-coded IP — Bypasses DNS entirely. Castiel can't see this, but PF could block it.
  8. Check NWPathMonitor status — Reads system reachability. Would report .unsatisfied in stealth mode. This is the key — malware using the system API would conclude there's no internet.

The Anti-Analysis Parallel

Interestingly, malware analysts see the opposite problem in sandboxes. Malware uses connectivity checks to detect fake internet (INetSim/FakeNet) and bail. From reverseengineering.app:

"A connectivity probe is a cheap, low-signal gate. If the world looks fake, the sample sleeps, exits, or withholds its real payload — denying the analyst the behaviour they were hoping to capture."

The stealth connectivity concept inverts this: instead of the attacker checking for fake internet to evade analysis, the defender makes the internet look fake to the attacker. The malware's own evasive behavior works against it.

The Mullvad VPN Precedent

Mullvad VPN already deals with this exact mechanism — and their solution proves the concept works. From their engineering docs:

"When macOS is coming back from sleep or connecting to a new WiFi network, it may try to send various requests over the internet before it publishes a default route to the routing table... The default route is only published when macOS finishes or times out its captive portal check."

Mullvad's solution was to run a custom resolver that only responds to captive portal domain queries, allowing macOS's probe to succeed while blocking all other DNS. This is the opposite of what we're proposing — Mullvad wants the probe to succeed so the system works normally.

Castiel could do the inverse: allow DNS resolution for everything except captive.apple.com, causing the probe to fail while all other DNS works through Castiel's proxy.

Proposed Mechanism: "Stealth Mode"

Concept

Castiel intentionally causes macOS's captive portal probe to fail during network association, inducing a persistent "no internet" state while DNS and connectivity actually work through Castiel's proxy.

Implementation Approaches

Approach A: DNS Blackhole for captive.apple.com

Castiel's DNS proxy returns NXDOMAIN (or 0.0.0.0) for queries to captive.apple.com and netcts.cdn-apple.com. macOS's probe can't resolve the host, so the HTTP GET never fires. The probe times out, and macOS enters the ! state. 

// In Castiel's DNS proxy handler:
if query == "captive.apple.com" || query == "netcts.cdn-apple.com" {
    return NXDOMAIN  // or return 0.0.0.0
}
// All other queries resolve normally through upstream DNS

Pros: Simple, no PF changes needed, works at the DNS layer. mDNSResponder caches the NXDOMAIN and doesn't retry.

Cons: If the system DNS is set to 1.1.1.1 directly (not through Castiel), this won't work — the query bypasses Castiel. Requires system DNS to be 127.0.0.1 or PF redirect to be active.

Approach B: PF Block for captive.apple.com IPs

Castiel adds a PF rule to block outbound TCP to Apple's captive portal IPs (17.253.27.0/24 range) on ports 80 and 443. The HTTP probe fails to connect, triggering the ! state. 

block drop out quick on en0 inet proto tcp from any to 17.253.27.0/24 port {80, 443}

Pros: Works regardless of DNS configuration. Blocks both HTTP and HTTPS probes.

Cons: Apple uses CDN and may change IPs. Need to resolve and update the block list. Also blocks legitimate Apple services on those IPs (though captive.apple.com is a dedicated endpoint).

Approach C: Transient Block During Network Association

Castiel blocks captive.apple.com for only ~10 seconds during daemon startup or when it detects a network state change (via SCNetworkReachability callbacks). This causes the probe to fail during the critical window, then removes the block so all other traffic works normally. 

// On network change event:
1. Block captive.apple.com (DNS NXDOMAIN or PF block)
2. Wait 10 seconds (probe timeout is typically 5-8 seconds)
3. Remove block
4. All other DNS continues working throughout

Pros: Minimal disruption. The block is transient — only long enough to fail the probe. After that, macOS won't re-probe until WiFi toggle.

Cons: Requires detecting network state changes. Race condition: if Castiel starts after the probe already succeeded, this won't work. Need to trigger on WiFi reconnect/sleep-wake events.

Approach D: HTTP Interception (Return Non-Success)

Castiel's PF rules redirect captive.apple.com:80 to a local listener that returns a non-"Success" response (or a redirect, which macOS interprets as a captive portal). This is the most precise approach — it only affects the probe, not other Apple services. 

rdr pass on en0 inet proto tcp from any to 17.253.27.0/24 port 80 -> 127.0.0.1 port 5380
// Local listener on 5380 returns: "Captive"
// (not "Success", so macOS thinks it's behind a captive portal)

Pros: Most surgical — only intercepts the probe, nothing else. Can return a redirect to trigger captive portal mode (which has stronger "limited connectivity" semantics).

Cons: Most complex to implement. Requires a local HTTP listener. Apple may also probe via HTTPS (port 443), which can't be redirected without TLS interception.

The Threat Model — Who Does This Defend Against?

Tier 1: Script Kiddies & Automated Malware Effective

Mass-distributed malware (Trojans, adware, commodity stealers) often includes a basic connectivity check before phoning home. These typically use InternetCheckConnection, getaddrinfo, or a simple curl. If the malware uses NWPathMonitor or SCNetworkReachability (which many macOS malware samples do, since it's the path of least resistance), stealth mode would cause them to conclude there's no internet and:

  • Sleep indefinitely (waiting for connectivity)
  • Exit without delivering payload
  • Show decoy behavior instead of real payload
  • Delay C2 registration, giving defenders time to detect

Tier 2: Organized Crime & APTs Partially Effective

More sophisticated threat actors (APT29, Gamaredon) perform multi-method connectivity checks. They may:

  • Try NWPathMonitor (fooled by stealth mode) AND raw socket connect (not fooled)
  • Use hard-coded IP addresses instead of DNS
  • Check scutil --nwi and compare with actual connectivity
  • Probe multiple endpoints and compare responses

Stealth mode adds friction — the malware has to work harder to determine connectivity, and its behavior may become more detectable (multiple probe attempts, unusual system calls).

Tier 3: Nation-State & Zero-Day Ineffective

Advanced adversaries with custom implants won't be fooled. They'll use raw sockets, hard-coded IPs, and may even check PF rules or running processes. Stealth mode provides no meaningful defense against these actors, but Castiel's DNS filtering still applies.

The "Honeypot" Angle

Key insight: Malware that detects "no internet" via NWPathMonitor but then tries to connect anyway (via raw socket or hard-coded IP) has just self-identified as sophisticated. Castiel could log this pattern: "Process X checked NWPathMonitor, got .unsatisfied, but attempted a network connection anyway." This is a high-confidence indicator of malicious behavior — legitimate apps that check reachability respect the result.

Risks & Trade-offs

User Experience Impact Moderate

  • Persistent ! on WiFi icon — Users may think their network is broken. This is the most visible side effect.
  • iCloud sync pauses — Files, photos, and notes won't sync until stealth mode is disabled.
  • Push notifications delayed — iMessage and other push-dependent apps may not receive messages promptly.
  • Software updates pause — macOS won't automatically check for or install updates.
  • App "offline" states — Many apps show offline banners or disable features.

Security Risks Requires Mitigation

  • Delayed security patches — If macOS updates don't auto-check, the system may miss critical patches. Mitigation: manually check for updates periodically, or schedule stealth mode to disable during maintenance windows.
  • False sense of security — Stealth mode doesn't actually block anything. Sophisticated malware bypasses it. Mitigation: present it as a layer, not a primary defense.
  • APNs delivery issues — MDM commands and Find My may not work. Mitigation: not suitable for MDM-managed devices.
  • Emergency services — If the system truly believes it's offline, emergency SOS features may not function. Mitigation: ensure cellular fallback works, or disable stealth mode on detected emergency calls.

Operational Risks Manageable

  • Non-deterministic — The ! state depends on timing. If Castiel starts after the probe already succeeded, stealth mode won't engage until the next WiFi reconnect.
  • Fragile — A WiFi toggle or reboot clears the state. Need to re-induce it on every network change.
  • Debugging difficulty — Other IT tools and support personnel may misinterpret the ! as a real network problem.
  • Apple may change behavior — Apple could add re-probing in a future macOS update, breaking stealth mode.

Legal & Ethical Considerations

  • Deception of system services — Intentionally causing macOS to report false connectivity state may violate Apple's developer guidelines or terms of use, especially if distributed as a product.
  • Enterprise environment — In a corporate setting, inducing fake "no internet" states could interfere with MDM, monitoring agents, and security tooling. Should only be used on personal or research machines.
  • Disclosure — If used in production, users should be informed that the ! is intentional and connectivity actually works.
  • Not a substitute for security — Stealth mode is a deception layer, not a replacement for actual security controls (firewall, EDR, DNS filtering).

Recommendation

Stealth mode is a viable defensive deception technique with real value as a secondary layer. It won't stop sophisticated attackers, but it adds friction for commodity malware and creates a detectable behavioral pattern for malware that tries to bypass it.

Recommended Implementation Path

  1. Phase 1 (Research): Implement Approach A (DNS NXDOMAIN for captive.apple.com) as a configurable option in Castiel. Test on a research machine to verify the ! state persists and DNS still works.
  2. Phase 2 (Detection): Add logging for processes that check NWPathMonitor but then attempt network connections. This "reachability bypass" pattern is a strong indicator of malicious behavior.
  3. Phase 3 (Automation): Use SCNetworkReachability callbacks to detect WiFi reconnects and sleep-wake events, automatically re-inducing stealth mode.
  4. Phase 4 (UX): Add a Castiel status indicator showing "Stealth Mode: Active" so the user understands the ! is intentional.
  5. Phase 5 (Hardening): Combine with PF rules to block raw socket connections to known malware C2 IPs, closing the bypass for hard-coded IP malware.

When NOT to Use

  • MDM-managed devices (breaks MDM check-in)
  • Devices that rely on Find My or emergency SOS
  • Servers or always-on machines that need automatic updates
  • Shared machines where other users would be confused by the !
  • Production environments where paused sync causes data loss

Open Questions for Further Research

  1. Does macOS Tahoe (26.x) have any re-probe mechanism that earlier versions lacked?
  2. What is the exact timeout for the captive portal probe? (Appears to be 5-8 seconds based on Mullvad's docs, but not officially documented.)
  3. Does the HTTPS probe to captive.apple.com:443 run in parallel with HTTP, or sequentially? If sequential, blocking only port 80 may be sufficient.
  4. Can SCNetworkReachability callbacks be used to detect when macOS is about to probe, allowing a just-in-time block?
  5. What percentage of macOS malware actually uses NWPathMonitor vs. raw socket checks? (Requires malware analysis lab testing.)
  6. Does Apple's Endpoint Security framework provide visibility into processes that query reachability state?
  7. Could stealth mode interfere with macOS's built-in malware protections (XProtect, Gatekeeper) that may need network access?
  8. What is the interaction between stealth mode and iCloud Private Relay (which has its own network path management)?
